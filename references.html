Attach your manuals, SDK documentation or internal engineering references. Rosetta makes them available to the coding agent alongside its normal file, edit and shell tools. The agent can look something up, apply it, and run the software to check its work.

01 / ATTACH A SOURCE

Your repository declares what it needs.

Add a rosetta.json file. Sources can describe an unfamiliar language, an internal DSL, a vendor SDK or a project API. No changes to the central agent are needed.

{
  "version": 1,
  "sources": [{
    "id": "internal-api",
    "title": "Internal API reference",
    "path": "docs/api.md",
    "kind": "internal",
    "file_patterns": ["*.widget", "src/*.js"],
    "priority": 10
  }],
  "commands": {"test": ["python3", "check.py"]}
}

Local search is deterministic and works offline. A hosted model still needs its provider connection. Rosetta does not fetch external documents or upload a catalog by itself.

02 / LET THE AGENT LOOK IT UP

Four tools. Used when useful.

ToolWhat it returns
reference_sourcesAvailable manuals, examples and project commands.
reference_searchSmall relevant passages, ranked with file context.
reference_readMore of a selected source, with line pagination.
reference_examplesCode examples from the attached references.

Results retain source paths, headings, line numbers, original URLs when supplied, and document hashes. Manuals stay out of the prompt until the agent requests a passage.

03 / REAL MUMPS, REAL EXECUTION

A payment service with a change to make.

The demo includes payment, storage and reporting routines. Give Rosetta a new task: make payments safe to retry without crediting the account twice. It can consult the bundled YottaDB documentation, edit the MUMPS source and execute checks against the actual interpreter.

export ROSETTA_CONTAINER=rosetta-reference-verify
bash scripts/bootstrap.sh
python3 examples/payments/verify.py
rosetta examples/payments

Requires Python 3.11+, OpenCode with a configured model, Docker and the WorldVistA/YottaDB image. The base demo passes its existing tests. The retry feature cases intentionally fail until the agent implements the requested behavior.

The verification runner compares output and captured database state, and rolls back each case. A passing finite suite establishes evidence for those cases.
